## Project
- VUS-OS is a Windows-style desktop in the browser. Main file: `index.html` (repo root). Local folder: `E:\Claude\VUS OS`.
- Repo: GitHub `Cra-Z-Gaming/VUS-OS`, branch main. It is NOT served by GitHub Pages: everything is fetched from raw.githubusercontent.com, so service workers and extra same-origin files can't be relied on.
- Layout: `index.html`, `upd.txt` (update history shown in What's new), `apps/` (native apps: notes.js, gallery.js, Terminal/terminal.js), `languages/` (list.json + one .js per language).
- Native apps get `(root, os)`; `os.sys` is built in `makeOS()` in index.html (files, folders, read/write/overwrite, launch, lang* helpers).
- Keep the user's style: plain-language comments, no mobile/touch features, no Paint app, SVG icons.
- Release steps: bump `OS_VERSION` in index.html and add an entry at the top of `upd.txt`, then push.

## Where things stand
- Languages system is written: `languages/python.js` (Pyodide in a Web Worker, runtime cached in Cache Storage so it works offline), `languages/list.json`, Terminal commands `install`, `uninstall`, `languages`, `py`/`python` (file or `-c`), Stop button and Ctrl+C, and `sys.overwrite` + `sys.lang*` in index.html.
- Python programs get the current folder's text files, including those in sub-folders (named like `data/a.txt`, up to 5 levels deep); changed or new text files are saved back, and sub-folders are created when a program makes `sub/a.txt`. `sys.exit()` and `exit()` end the program cleanly. `py file.py a b` sets `sys.argv`; `py -V` shows the version; `sys.stdin` reads typed lines.
- `input()` works in Python (pauses via Pyodide JSPI, needs recent Chrome/Edge; other browsers get EOF) and in JavaScript (`await input("q")`). The Terminal sends the next typed line to the running program (`inputWait` in terminal.js) and hides command suggestions meanwhile.
- `languages/javascript.js` is written: runs `.js` files with `js file.js` or `js -c "code"` (also `-e`) in a Web Worker, no download. Programs get `console.*`, `await input()`, `fs.list/exists/read/write`, top-level await, timers. `fmt` keeps short objects on one line.

### Step 2 (next, big): the VM  (design written Nov 15 2026, not started in code)
Goal: a window that runs a COPY of the OS where the user can edit the system files, with no way to touch the real files. Reset to default and Import an OS file must be safe, because an imported OS is untrusted code.

Design decisions (reasons included so they can be changed):
- Isolation: run the VM OS in an `<iframe sandbox="allow-scripts">` loaded from a `blob:` URL, WITHOUT `allow-same-origin`. It then gets an opaque origin: it cannot read the real localStorage, IndexedDB, cookies or the parent's DOM. A same-origin iframe or a different storage prefix is NOT enough (same origin = the code could read the real `vos2` keys). The parent talks to it only with `postMessage`.
- Storage inside the VM: the sandbox has no real storage, so the OS needs a storage adapter. First read how `LS`/`save` (localStorage), `dbGet`/`dbSet`/`dbDel` (IndexedDB stores `files` and `code`) and `GUEST` / `NS` (index.html, near line 366) work, then route them through one adapter object: normal mode = today's behaviour, VM mode = in-memory Maps. Guest mode already shows the pattern (separate `NS`), but it is same-origin, so it is not enough for imported code.
- Where the VM OS code comes from: the parent fetches `OS_REPO + "index.html"` (or the user's imported/edited copy), puts a small prelude in front (`window.__VM = { overlay }`), and loads that as the blob. The prelude wraps `fetch` so any URL under `OS_REPO` that is in `overlay` (a map of path to text: `apps/notes.js`, `languages/python.js`, `upd.txt`, even `index.html`) returns the edited text instead of the repo's. Native apps and languages are fetched and `import()`ed from blobs already, so editing them works without more changes.
- Editing system files: inside the VM, `C:\System` is writable (the read-only rule stays in the real OS). Saving a system file changes the overlay, shown with an "edited" mark. `index.html` is edited as an overlay entry too; "Restart VM" rebuilds the blob from the overlay. Show a clear red VM badge in the VM's taskbar (`window.__VM` set) so nobody mixes it up with the real OS.
- The VM manager window (real OS side, new app "Virtual Machine"): Start / Restart, Reset to default (clears the overlay), Import OS (a .zip or .json bundle of the overlay: validate paths, size limits, text only, never executed outside the sandbox), Export OS (the overlay as a .zip or .json), and a list of edited files. Open question for the user: should edits survive closing the tab? Proposed default: YES, the overlay (text only, never run outside the sandbox) is kept in the real OS storage under its own key so Reset is one click, while the VM's own files and settings are thrown away on close.
- The sandbox can still make network requests (fetch to any site that allows CORS). It can only leak what is inside the VM, which is nothing real. If wanted later, add a CSP meta tag in the blob with `connect-src` limited to the repo.
- What storage looks like (read Nov 15 2026): `LS`/`save` use `localStorage` with the prefix `NS` (`vos2`, or `vosg` in Guest mode, which is set by `sessionStorage.vos_guest`). All IndexedDB use goes through `idb` + `dbGet` / `dbSet` / `dbDel` (stores `code` and `files`, near line 670); the only other direct use is `wipeNs()` (factory reset, real mode only). In a sandbox without `allow-same-origin`, `localStorage`, `sessionStorage`, `indexedDB` and Cache Storage all throw. So: the VM prelude must define in-memory `localStorage` and `sessionStorage` objects (via `Object.defineProperty(window, ...)`) before the OS script runs, and the DB layer uses `MEMDB` (step 2a, done). `save()` has no try/catch, so the prelude must supply working objects. Python can't be installed inside the VM (it caches in Cache Storage); that is acceptable.
- Build order: (2a) DONE, not tested: `MEMDB` in index.html (in-memory maps used by dbGet/dbSet/dbDel when `window.__VM` is an object; no change in normal mode; test that the real OS still works); (2b) DONE, tested only in Node (a vm sandbox: storage Proxy, Object.keys, overlay fetch hit and pass-through, hostile overlay can't close the script tag, path checks), NOT in a browser: `cleanOverlay`, `vmPrelude`, `buildVmHtml`, `vmBuild(overlay)` in index.html (before `runInTerminal`). `vmBuild` downloads the repo's index.html, so the VM only works after the new index.html (with `MEMDB`) is pushed. Quick browser test from the DevTools console, no UI yet: `vmBuild({}).then(u => { const f = document.createElement("iframe"); f.setAttribute("sandbox", "allow-scripts"); f.src = u; f.style = "position:fixed;inset:0;width:100%;height:100%;z-index:99999;border:0;background:#000"; document.body.appendChild(f); })` (remove it with `document.querySelector("iframe[sandbox]").remove()`). The OS inside should boot with empty storage; check the real OS's files are not visible in it; (2c) DONE, syntax-checked only, NOT tested in a browser: `VMAPP` ("Virtual Machine" window: Start / Restart / Stop / Full screen, status line, sandboxed iframe from `vmBuild(LS("vmOverlay", {}))`, listens for `{vus:"vm-ready"}` by `e.source`, closing the window stops the VM) listed in the Start rail, the taskbar right-click menu, `sysApps`, `SYS_APPS` and `makeOS().apps`; inside the VM (`window.__VM`) a red "VM" badge is put in the taskbar and the ready message is posted; the `vmOverlay` key is read but nothing writes it yet (2d/2e); (2d) writable `C:\System` inside the VM + Save to overlay; (2e) Reset / Import / Export; (2f) security review of import (path checks, size limits, no `..` paths).
- Needs a real-browser test at every step; a blob-URL iframe without `allow-same-origin` also cannot use some APIs (clipboard, `localStorage` throws), so the VM OS must wrap every storage access in try/catch.

## Known limits (by design for now)
- Python `input()` needs a browser that can pause WebAssembly (recent Chrome/Edge); elsewhere it ends with EOF.
- A JavaScript program stuck in a tight loop can only be ended with Stop / Ctrl+C (the worker is terminated).
- A `|` inside code splits the Terminal line; use `;` instead.
- Python `urllib` and `requests` work through `pyodide-http` (patched automatically when the code mentions them; downloads that small package once). Not tested in a real browser yet. The server must allow cross-origin requests (CORS), including the `Authorization` header, or the browser blocks the call. JavaScript uses plain `fetch`, Python can also use `pyodide.http.pyfetch`.
- Output stops at 3000 lines; files over 1 MB and non-text files are not given to programs. Programs can't delete files or folders (only create/change text files); empty folders a program makes are not saved.
